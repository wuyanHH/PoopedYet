# 自我审查：遗漏点与优化点

对现有方案（技术选型 + 数据模型 + 16 页视觉稿）做的一轮系统性挑刺。
分「已修」「阻塞项」「建议项」「工程与合规」「体验优化」。

**结论先说**：设计层面的东西基本齐了，但**接下来写代码前有 4 个必须先定的问题**，
它们都是「现在改一分钟，以后改要迁移数据」的类型。

## 一、本轮已修

### 0. 日历写死 5 行，3/12 个月会丢日期 ★★★

最严重的一个，而且**是被"刚好的样例数据"藏住的**。

日历网格是 `for (let i = 0; i < 35; i++)` —— 永远 5 行 35 格。
但月份需要几行取决于「1 号是周几」和「这个月有多少天」：

```js
const rows = Math.ceil((offset + days) / 7);   // 可能是 5，也可能是 6
```

2026 年的实际情况：

| 月份 | 1 号 | 偏移 | 天数 | 行数 | 旧代码后果 |
|---|---|---|---|---|---|
| 3 月 | 周日 | 6 | 31 | **6** | 丢掉 3/25–3/31 |
| 8 月 | 周六 | 5 | 31 | **6** | 丢掉 8/25–8/31 |
| 11 月 | 周日 | 6 | 30 | **6** | 丢掉 11/24–11/30 |

**全年 3/12 个月受影响，每个月丢一整个星期。**

为什么一直没发现：视觉稿的样例月份是 2026 年 2 月 —— 周日开头 + 28 天 = 34 格，
**正好落在 5 行以内**。用刚好合适的数据去验证，等于没验证。

已修（行数按月份实算），并新增第 ⑲ 屏专门画 2026 年 8 月来盯这个边界。

### 1. 对比度：355 处不合格 → 0 处

色值全是手挑的，而 WCAG 对比度**不可能靠肉眼看出来**。我写了
[`.design/contrast-check.js`](../.design/contrast-check.js)，遍历全部 690 个文本节点
和 313 个图标，按 WCAG 2.1 AA 判定（普通文本 4.5:1，大字 3:1，图标 3:1）。

首次运行结果：**文本 355 处不合格、图标 50 处不合格**。整个二三级文字层偏浅约 35%。

| 令牌 | 原值 | 新值 | 原来 | 现在 |
|---|---|---|---|---|
| `--ink-3` 三级文字 | `#A2937F` | `#756552` | 2.76:1 ✗ | 5.17:1 ✓ |
| `--brand` 当文字用 | `#C8783C` | 拆出 `--brand-ink: #9A5219` | 3.11:1 ✗ | 5.38:1 ✓ |
| 焦糖底 + 白字 | `#C8783C` | 拆出 `--brand-fill: #A85F29` | 3.38:1 ✗ | 4.85:1 ✓ |
| 主按钮/FAB 渐变 | `#D98B4C→#B4662F` | `#B05F2C→#9A5219` | 2.71:1 ✗ | 4.65:1 ✓ |
| 休 角标 | 浅红底 + 红字 | `#B03A2E` 实心 + 白字 | 3.27:1 ✗ | 6.01:1 ✓ |
| 班 角标 | 浅蓝底 + 蓝字 | `#4A7C8C` 实心 + 白字 | 3.80:1 ✗ | 4.61:1 ✓ |
| `--live` 正在屙 | `#4E8C6A` | `#3F7A57` | 3.97:1 ✗ | 5.08:1 ✓ |

两条顺手得到的改进：

- **`--brand` 拆成了三个令牌**，按用途分家，不再是"一个焦糖色到处用"：
  `--brand`（仅 ≥24px 大字 / 纯装饰）、`--brand-ink`（焦糖色**文字**）、
  `--brand-fill`（焦糖色底、上面放**白字**）。
- **休/班 角标从 8.5px 浅底彩字改成 10px 实心药丸**。彩字在浅底上小到 8.5px 时，
  对比度和可认性双输；实心白字药丸两个问题一起解决，字号还涨了 18%。

非本月的日期是有意降级的，给它们加了 `a11y-dim-ok` 标记，自检会归到
「已声明降级」而不是失败——否则每次跑检查都会被这 21 格淹没。

顺带清掉一个死令牌 `--brand-deep`（已被 `--brand-fill` 取代，只剩定义无人引用）。

### 2. 「没有结束时间」被当成「进行中」

上一轮已修，记在 [tech-stack.md](tech-stack.md) 的状态机一节。这里只重复结论：
`endedAt` 为空**不等于**进行中，加 `endUnknown` 字段并修正唯一索引，

## 二、阻塞项：已全部定案

> 这一节原来列的是「写代码前必须定」的问题。四个都已经定了，
> 结论写进了 [design-system.md §9a / §9d / §9e](design-system.md)。
> 下面保留当时的分析，以及最终选择。

### P0-1 全新安装时一个屙屎人都没有 ✅ 已定

FAB「现在开屙」依赖"默认屙屎人"，但**首次启动时数据库是空的**。
点 FAB 会发生什么？没有定义。视觉稿里的「空状态」画的是"某天没记录"，
不是"还没有建过人"。

**决定：静默自动创建 `Pooper{name:'我', isDefault:true}`，不弹引导页。**
主页日历下方放一条可关闭的提示条（⑳）交代"还能加人"。

理由：这个 App 的核心动作是"一次点击开屙"。在它前面竖一道"先填名字选头像"的墙，
是用最贵的位置解决最便宜的问题。而且单人用户会觉得完全多余。

**重要的衍生发现**：这个逻辑不能只写在首启分支里 ——
**归档掉最后一个人也会回到"一个都没有"**（见 P0-2）。
所以必须抽成 `ensureDefaultPooper()`，两个时机都调。

### P0-2 删除屙屎人会连带删掉他的全部历史 ✅ 已定

数据模型只写了备注的级联，**从没定义 pooper 删除时记录怎么办**。
按最自然的写法（外键 CASCADE），删掉"阿狗"会静默抹掉他几百条记录。

**决定：删除 = 归档**（`archivedAt`）。历史原样保留，不再出现在选择器里，
但**日历徽标和统计仍然计入**（否则日历数字会莫名变小，用户会以为数据丢了），
用低饱和显示，"隐藏已归档"做成设置项。归档可撤销。
真要彻底删除，放进设置页「危险操作」，明确告知会删掉 N 条记录。

### P0-3 `isDefault` 没有唯一性约束 ✅ 已定

多个屙屎人可以同时 `isDefault = true`，或者一个都没有（删掉了默认那个）。

**决定**：部分唯一索引 + 两条边界规则。

```sql
CREATE UNIQUE INDEX ux_default ON poopers(is_default) WHERE is_default = 1;
```

1. 归档 / 删除默认人时，自动把**剩下最早创建**的那个人提升为默认
2. 如果一个人都不剩，`isDefault` 全为 null（然后触发 P0-1 的守卫）

### P0-4 系统字体缩放会撑爆日历格 ✅ 已定

日历格是**固定 58px 高**，里面塞了日期 + 角标 + 头像 + 计数。
Android 上把系统字体调到 130%~200% 很常见。

**先算了实际代价，结论比预想的严重**：

| 系统档位 | 单格需要 | 6 行月份共需 | 剩给记录列表 |
|---|---|---|---|
| 1.0× | 58px | 363px | 充足 |
| 1.3×（大） | ~67px | 417px | 约 136px |
| 2.0×（最大） | **~77px** | **477px** | **约 76px — 列表基本没了** |

安卓可用高度约 553px。**所以「格高自适应」不是懒不懒的问题，是 2.0× 时日历会吃掉 477px、
记录列表彻底消失 —— 等于用一个功能换掉另一个功能。**

**决定：日历格内字号上限 1.3×，另在设置页给「日历字号」独立三档兜底。**

选 1.3 的理由：安卓字体档位是 `1.0 / 1.15 / 1.3 / 1.5 / 2.0`，
1.3 正好是「大」这一档，**常用需求全覆盖**，只有「特大 / 最大」会被截住。
日历卡外围的文字（月份标题、星期头、日期栏）正常跟随系统，只有格子内部被钳制。

## 三、建议项：影响可用性

### P1-1 持久通知 + 快捷磁贴 ★ 这是"忘了点结束"的根治方案

现在的方案是**事后追问**（打开 App 弹"还在屙吗？"）。
更好的做法是**从事后补救变成事前提醒**：

- 开始记录时发一条**常驻通知**：「正在屙 · 00:06」，展开有「结束」按钮。
  用户从通知栏一点就结束，根本不用打开 App。
- Android 快捷设置磁贴（Quick Settings Tile）：下拉一下就能"开屙"。

这两个加起来，让"打开 App 点结束"这个动作彻底消失，
**「待确认」这个状态大概会少出现 90%**。

成本：Android 13+ 需要 `POST_NOTIFICATIONS` 运行时权限；
前台服务通知需要 `FOREGROUND_SERVICE`（如果用前台服务保活）。

### P1-2 没有撤销（Undo）

「现在开屙」是**一次点击直接落库**的（这是它的手感关键，不该改）。
但误触之后没有任何退路，用户得去详情页删掉。

加一个 SnackBar「已开始记录 · 撤销」就行，成本极低。

### P1-3 色盲可及性

日历格靠**头像底色**区分屙屎人。红绿色盲（男性约 8%）会分不清
`#F7E5D2` 焦糖和 `#E1EDE5` 苔绿。

图标的形状差异是兜底，但只有 9px——这正好和 design-system 待定项第 3 条是同一个问题。
**两条线索（颜色 + 形状）都不可靠时，需要第三条**：建议把"非本月"以外的头像
统一加一圈深色描边、或在日历格里改用**姓名首字**（中文单字在 9px 下的区分度远高于线条图标）。

### P1-4 本地化没配

Flutter 的 Material 日期/时间选择器**默认是英文**。补录页要用到
`showDatePicker` / `showTimePicker`，不配的话会突然冒出一个英文弹窗。

需要：`flutter_localizations` 依赖 + `localizationsDelegates` +
`supportedLocales: [Locale('zh','CN')]`。

### P1-5 时区

日历聚合查询用了 `date(started_at, 'localtime')`，依赖设备时区。
国内没有夏令时，问题不大，但**出国后历史记录会整体平移**（东京比北京早 1 小时，
23:30 的记录会跑到第二天）。

建议存 **UTC 时间戳**，查询时按本地日切分。成本很低，现在做等于免费。

### P1-6 「正在屙」的记录如果跨天了，用户会找不到它 ★

既然定了按 `startedAt` 归属，那昨天 23:50 开始、现在还没结束的记录，
会**留在昨天的列表里**。用户切到今天，看不到它，也就想不起来去结束。

需要在今天也放一条提示：「阿狗有一次从昨天 23:50 开始还没结束」。
这是 `startedAt` 归属方案的必然副作用，必须在 UI 上补掉。

## 四、工程与合规

### P2-1 Drift 迁移策略没写

没有 `schemaVersion` 和 `MigrationStrategy` 的方案，等于第一版发布后
**每次改表都会让老用户数据丢失**。需要在第一版就把迁移框架搭好，哪怕迁移是空的。

### P2-2 头像文件的存储与备份

存文件路径的话，重装 App / 换机恢复后路径会失效，头像全变默认。

建议：**把 96px 缩略图直接以 BLOB 存进 SQLite**（几十 KB，几百个屙屎人才几 MB）。
原图不必存。这样导出 JSON 时头像跟着走，备份天然完整。

### P2-3 测试策略

三个最容易错、且错了很难发现的地方，必须有单元测试：

1. 日历网格的**起始偏移与 5/6 行判定**（月份天数 + 每月 1 号是周几的组合）
2. **节假日三态**渲染（休 / 班 / 无，注意 `isOffDay=false` 的那批恰好是周末）
3. **记录状态机**的四个状态转换，尤其是超阈值自动收敛

### P2-4 节假日数据每年要更新

打包进 APK 的代价是：**每年国务院一发公告，就必须发一次新版本**，否则次年日历失准。

建议在设置页（⑭ 节假日与日历）加一个「**导入节假日 JSON**」入口。
这样紧急情况下用户能自己补，不必等发版。

### P2-5 导出 JSON 缺 schema 版本号

没有版本号的导出文件，将来无法安全导入（字段变了就不知道该怎么解析）。
在导出结构顶层加 `{ "schemaVersion": 1, "exportedAt": ..., "data": {...} }`。

### P2-6 targetSdk

Google Play 要求新应用 target 较新的 API level（当前需 35+）。
`compileSdk 36` / `targetSdk 35` 是安全的起点。

### P2-7 自适应图标

需要前景 / 背景两层，108dp 画布 + 中间 72dp 安全区。
「屙」字必须完全落在安全区内，否则会被各厂商的图标形状裁掉一部分。
Play 商店另需 512×512 的方形图。

### P2-8 中国区 APP 备案

如果打算上国内安卓商店（应用宝 / 华为 / 小米 / OPPO / vivo），
2023 年 9 月起新 App 需要完成**工信部 APP 备案**，个人开发者同样适用。
只做 APK 直传（发给朋友装）不经过应用商店的话，不涉及这一条。

纯本地、不联网、不收集数据，这个备案流程会简单很多，但仍需完成。

## 五、体验优化

### 1. 布里斯托大便分类法做成默认备注预设 ★

「默认备注」现在全是自由文本（拉肚子 / 很顺畅…），价值有限。
而**布里斯托大便分类法**是消化科通用标准，分 7 型：

| 型 | 描述 | 含义 |
|---|---|---|
| 1 | 硬球状，难排出 | 严重便秘 |
| 2 | 香肠状但结块 | 轻度便秘 |
| 3 | 香肠状，表面有裂纹 | 正常 |
| 4 | 光滑柔软香肠状 | 理想 |
| 5 | 柔软团块，边缘清晰 | 偏稀 |
| 6 | 糊状，边缘不齐 | 轻度腹泻 |
| 7 | 水样，无固形物 | 严重腹泻 |

它天然适配"一个人可以有多条备注"的结构，而且让这个 App 从"玩梗"变成
**真的有健康记录价值**。作为内置预设（可删）比让用户自己打"拉肚子"强得多。

### 2. 连续记录天数 / 月度小结

习惯类产品的留存核心。数据都已经有了，统计页加一个"连续 N 天"成本很低。

### 3. 日历格的触控目标偏小

46×58dp，宽度低于 Material 建议的 48dp 最小值。
可以靠格子间距补足命中区域（把 gap 也算进点击热区），需要在实现时注意。

### 4. 读屏（TalkBack）语义标签

日历格现在是"11"+头像，读屏会念成孤零零一个数字。
需要 `Semantics(label: '2月11日 周三，4 次记录')`。
整个 App 的语义标签目前都没设计过，实现时补。

### 5. 死代码

`.minical` 系列 CSS（4 处）没有任何标记引用，是早期版本的残留，可以删。

## 六、我还没做的事 / 不确定性

诚实列一下这轮**没有**验证的东西：

1. **视觉稿只在桌面 Chrome 里验证过布局**，没在真机上看过。
   阴影、圆角、得意黑的实际渲染效果，以及 9px 图标的可辨识度，都需要真机确认。
2. **对比度检查覆盖的是视觉稿，不是将来的 Flutter 实现**。
   Flutter 里的 `Color` 常量需要复用同一套令牌，否则这个检查就白做了。
   建议把令牌导出成一份 Dart `ThemeExtension`，两边同源。
3. **没有做性能与体积评估**。目前看 Drift + 图片 BLOB 的方案，10 年数据量（约 1 万条记录）
   对 SQLite 来说微不足道，但没有实测。
4. **没有验证节假日的真实数据源**能否正常抓取（本轮网络对 `raw.githubusercontent.com` 是受限的）。
   当前视觉稿里的 2026 年春节（2/15–2/23 休、2/14 与 2/28 班）来自搜索结果，标记为示意值。
5. **没有确认"一台设备记全家"这个前提**。多个屙屎人的设计隐含了这个假设。
   如果实际是每人一台手机各自记录，那本地存储的方案完全不成立，需要同步——
   这是唯一一个会推翻整个架构的问题，值得先确认。
